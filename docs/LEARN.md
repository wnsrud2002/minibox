# minibox로 배우는 컨테이너와 TCP

이 문서는 minibox를 처음 보는 사람이 **컨테이너가 어떻게 동작하는지**, **TCP가 패킷 손실을 어떻게 견디는지**를 처음부터 이해할 수 있게 쓴 학습 가이드다. 각 장은 같은 순서로 되어 있다.

1. **배경지식**: 이 장을 이해하는 데 필요한 개념
2. **원리**: 리눅스 커널이 실제로 하는 일
3. **minibox에서는**: 어떤 코드로 구현했나
4. **직접 확인**: 눈으로 볼 수 있는 명령
5. **겪은 문제**: 만들면서 실제로 막혔던 곳

리눅스 명령어(`ls`, `ps`, `cat`)와 프로그래밍 기초만 알면 읽을 수 있다. 앞 장의 내용을 뒤 장에서 쓰므로 순서대로 읽기를 권한다.

## 0. 큰 그림

### 가상 머신과 컨테이너의 차이

**가상 머신(VM)** 은 하드웨어를 흉내 내고, 그 위에서 운영체제(커널)를 통째로 하나 더 돌린다. 격리는 강하지만 무겁다. 켜는 데 수십 초가 걸리고 메모리도 GB 단위로 쓴다.

**컨테이너** 는 커널을 새로 띄우지 않는다. 호스트의 커널을 그대로 같이 쓰면서, 커널에게 "이 프로세스에게는 세상을 이렇게 좁게 보여 줘"라고 부탁할 뿐이다. 그래서 가볍고 거의 즉시 뜬다.

```
   가상 머신                          컨테이너
┌─────────┐┌─────────┐          ┌─────────┐┌─────────┐
│  앱 A   ││  앱 B   │          │  앱 A   ││  앱 B   │
├─────────┤├─────────┤          └────┬────┘└────┬────┘
│ 커널 A  ││ 커널 B  │               │  격리 설정 │
├─────────┴┴─────────┤          ┌────┴──────────┴────┐
│   하이퍼바이저     │          │   호스트 커널 하나   │
├────────────────────┤          ├────────────────────┤
│      하드웨어      │          │      하드웨어      │
└────────────────────┘          └────────────────────┘
```

### 컨테이너를 이루는 세 가지 기술

리눅스에 "컨테이너"라는 단일 기능은 없다. 컨테이너는 아래 세 기능을 조합한 결과다. Docker도 결국 이 세 가지를 호출한다.

| 기술 | 질문 | minibox 주차 |
|---|---|---|
| **네임스페이스(namespace)** | 무엇이 **보이는가**? (프로세스, 호스트네임, 네트워크, 마운트) | 1, 2, 4주차 |
| **cgroup** | 얼마나 **쓸 수 있는가**? (메모리, CPU, 프로세스 수) | 3주차 |
| **루트 파일시스템 교체** | 어떤 **파일**이 있는가? (alpine 이미지) | 2주차 |

그래서 컨테이너 안에서 도는 프로그램도 호스트에서 보면 그냥 평범한 프로세스다. minibox로 컨테이너를 띄운 뒤 호스트에서 `ps aux | grep sleep`을 치면 컨테이너 안의 `sleep`이 그대로 보인다. 컨테이너 **안에서는** 호스트가 안 보이지만, 호스트에서는 컨테이너가 다 보인다. 격리는 한 방향이다.

## 1. 프로세스 격리: 네임스페이스

### 배경지식

- **프로세스와 PID:** 실행 중인 프로그램 하나가 프로세스이고, 커널이 붙여 주는 번호가 PID다. `echo $$`는 지금 쉘의 PID를 보여 준다.
- **PID 1(init):** 부팅할 때 커널이 가장 먼저 띄우는 프로세스다(보통 systemd). 부모를 잃은 프로세스(고아)를 입양하고, 이들이 끝나면 뒷정리(reap)를 한다.
- **fork와 exec:** 새 프로세스는 `fork`(복제)로 만들고, `exec`로 다른 프로그램으로 **갈아 끼운다**. exec를 하면 PID는 그대로 두고 내용물만 바뀐다. 리눅스에서는 fork 대신 더 많은 옵션을 받는 `clone`이라는 시스템 콜을 쓴다.

### 원리

네임스페이스는 커널 자원 하나를 **여러 벌로 복사해서 프로세스마다 다른 벌을 보여 주는** 기능이다. 새 프로세스를 `clone`할 때 플래그를 주면, 그 프로세스는 새 네임스페이스 안에서 태어난다.

| 네임스페이스 | clone 플래그 | 분리되는 것 | minibox |
|---|---|---|---|
| PID | `CLONE_NEWPID` | 프로세스 번호. 안에서 첫 프로세스가 PID 1이 된다 | ✅ |
| UTS | `CLONE_NEWUTS` | 호스트네임 | ✅ |
| Mount | `CLONE_NEWNS` | 마운트 목록(어떤 디스크가 어디에 붙었나) | ✅ |
| Network | `CLONE_NEWNET` | 네트워크 장치, IP, 라우팅 표, 방화벽 규칙 | ✅ |
| IPC | `CLONE_NEWIPC` | 공유 메모리, 메시지 큐 | ✅ |
| User | `CLONE_NEWUSER` | 사용자 ID. 안에서는 root지만 밖에서는 일반 사용자 | ❌ (root로 실행) |
| Cgroup | `CLONE_NEWCGROUP` | cgroup 경로가 보이는 방식 | ❌ |
| Time | `CLONE_NEWTIME` | 부팅 이후 시간 | ❌ |

PID 네임스페이스에서는 **같은 프로세스가 두 개의 번호를 가진다.** 컨테이너 안에서는 PID 1이고, 호스트에서는 예를 들어 3804773이다. `/proc/<PID>/status`의 `NSpid:` 줄에서 두 번호를 동시에 볼 수 있다.

```
NSpid:  3804773  1
        ↑ 호스트  ↑ 컨테이너 안
```

두 프로세스가 같은 네임스페이스에 있는지는 `/proc/<PID>/ns/` 아래 링크를 보면 안다. 링크 값의 숫자(inode)가 같으면 같은 네임스페이스다.

```bash
$ readlink /proc/self/ns/pid
pid:[4026531836]      # 호스트
$ sudo readlink /proc/3804773/ns/pid
pid:[4026532519]      # 컨테이너: 숫자가 다르다 = 분리됨
```

### minibox에서는: re-exec 패턴

`internal/container/run.go`

```
minibox run alpine sh
   │
   │ ① clone(NEWPID|NEWUTS|NEWNS|NEWNET|NEWIPC)로
   │    자기 자신(/proc/self/exe)을 "init" 모드로 다시 실행
   ▼
minibox init  (새 네임스페이스 안, PID 1)
   │ ② 호스트네임 변경, 루트 파일시스템 교체, /proc 마운트
   │ ③ exec("sh")  → 자기 자신을 sh로 갈아 끼움
   ▼
sh  (여전히 PID 1)
```

**왜 자기 자신을 다시 실행할까?** 네임스페이스는 `clone`할 때 만들어진다. 그런데 설정 작업(호스트네임 바꾸기, 마운트 등)은 **새 네임스페이스 안에서** 해야 한다. 그래서 부모는 네임스페이스를 만들어 자식을 띄우는 일만 하고, 자식이 안에서 나머지를 한다.

Go에서는 이게 특히 중요하다. Go 프로그램은 항상 여러 스레드로 돌아가는데, 이미 실행 중인 프로세스를 네임스페이스로 옮기는 `setns`/`unshare`는 호출한 **스레드 하나에만** 적용된다. 처음부터 새 프로세스로 띄우면 이 문제가 없다. runc(Docker가 쓰는 런타임)도 같은 방식을 쓴다.

### 직접 확인

```bash
sudo ./minibox run alpine /bin/sh
/ # echo $$        # 1
/ # hostname       # minibox
/ # ps             # 자기 프로세스만 보인다 (2장의 /proc 재마운트 덕분)
```

`sudo ./minibox serve` 대시보드의 네임스페이스 표는 위의 inode 비교를 자동으로 해서 보여 준다.

### 겪은 문제: PID 1은 시그널을 무시한다

`timeout 5 무한루프`를 컨테이너에서 돌렸더니, 5초가 지나도 끝나지 않았고 Ctrl+C도 먹지 않았다.

커널은 PID 1을 보호한다. PID 1이 **처리 함수(핸들러)를 등록하지 않은 시그널**은 같은 네임스페이스 안에서 보내면 버려진다. 보통 프로그램은 SIGTERM이나 SIGINT를 받으면 기본 동작으로 죽는데, PID 1은 그 기본 동작이 적용되지 않는다. init이 실수로 죽으면 시스템 전체가 멈추기 때문이다.

busybox의 `timeout`은 자기 자신을 명령으로 exec하는 방식이라, 무한 루프가 PID 1이 되어 버렸다. 이것이 **Docker에 `--init` 옵션이 있는 이유**다. 이 옵션을 주면 tini 같은 작은 init이 PID 1을 맡아 시그널을 전달하고 고아를 거둔다. minibox는 부모 쪽에서 시그널을 받아 컨테이너를 SIGKILL로 끝내도록 해서 해결했다.

## 2. 파일시스템 격리: pivot_root와 overlayfs

### 배경지식

- **마운트:** 리눅스에서는 모든 파일이 `/` 아래 트리 하나에 매달려 있다. 디스크나 가상 파일시스템을 트리의 한 디렉터리에 붙이는 것을 마운트라고 한다. `/proc`도 디스크가 아니라 커널이 만들어 내는 가상 파일시스템이다.
- **루트 파일시스템(rootfs):** 컨테이너 이미지의 정체는 `/bin`, `/etc`, `/lib` 같은 디렉터리를 담은 **폴더 하나**다. minibox는 alpine 리눅스의 minirootfs(약 8MB)를 `images/alpine/`에 풀어서 쓴다.

### 원리 1: chroot가 아니라 pivot_root

`chroot`도 루트 디렉터리를 바꿀 수 있지만, 기존 루트는 여전히 마운트된 채 남는다. 그래서 탈출 방법이 알려져 있다. `pivot_root`는 **루트 마운트 자체를 교체**한다.

```
pivot_root(new_root, put_old)

   전:  /  (호스트)             후:  /  (= 예전 new_root, alpine)
        └─ tmp/.../merged            └─ .oldroot  (= 예전 호스트 /)
                                          ↓ umount 해서 떼어 냄
                                     이제 호스트 파일에 닿을 길이 없다
```

순서는 이렇다. ① 새 루트로 옮기고, ② 옛 루트를 `/.oldroot`에 잠깐 붙여 뒀다가, ③ 떼어 내고 디렉터리까지 지운다.

### 원리 2: 마운트 전파(propagation)

mount 네임스페이스를 새로 만들어도, 호스트의 `/`가 **shared** 상태면 컨테이너 안에서 한 마운트가 호스트로 새어 나간다. 요즘 리눅스(systemd)는 기본값이 shared다. 그래서 가장 먼저 `/`를 **private**으로 바꾼다.

```go
syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, "")
```

### 원리 3: /proc 다시 마운트

`ps`는 `/proc` 디렉터리를 읽어서 프로세스 목록을 만든다. PID 네임스페이스를 나눠도, `/proc`이 호스트의 것이면 `ps`에 호스트 프로세스가 전부 보인다. 새 PID 네임스페이스 안에서 `/proc`을 **새로 마운트**해야 자기 프로세스만 보인다.

### 원리 4: overlayfs, 이미지는 공유하고 변경은 따로

컨테이너를 10개 띄울 때마다 이미지를 10번 복사하면 느리고 낭비다. overlayfs는 여러 디렉터리를 **겹쳐서 하나처럼** 보여 준다.

```
merged/  ← 컨테이너가 보는 /  (lower 위에 upper를 겹친 모습)
   ▲
   ├── upper/  읽기·쓰기. 이 컨테이너가 바꾼 것만 쌓인다 (/tmp/minibox-<id>/upper)
   └── lower/  읽기 전용. 원본 이미지 (images/alpine) — 모든 컨테이너가 공유
   (work/  overlayfs가 내부 작업용으로 쓰는 빈 디렉터리)
```

- **읽기:** upper에 없으면 lower에서 읽는다.
- **수정(copy-up):** lower에 있는 파일을 고치면, 먼저 upper로 복사한 뒤 복사본을 고친다.
- **삭제(whiteout):** lower의 파일을 지우면 upper에 "지워졌음" 표시(whiteout, 0/0번 문자 장치)를 만든다. 원본은 그대로 있다.

Docker 이미지의 "레이어"가 바로 이 lower를 여러 겹 쌓은 것이다.

### 원리 5: /dev는 최소한만

alpine rootfs의 `/dev`는 비어 있다. 그렇다고 호스트의 `/dev`를 통째로 보여 주면 컨테이너가 디스크(`/dev/nvme0n1`) 같은 장치를 직접 건드릴 수 있다. 그래서 tmpfs(메모리 파일시스템)를 올리고 `null`, `zero`, `full`, `random`, `urandom`, `tty` 여섯 개만 `mknod`로 만든다.

### minibox에서는

`internal/container/run.go`의 `setupRoot`, `setupDev`. 마운트는 모두 컨테이너의 mount 네임스페이스 안에서 일어난다. 그래서 컨테이너가 끝나면 **커널이 알아서 전부 걷어 낸다.** minibox는 upper 디렉터리만 지우면 된다.

### 직접 확인

```bash
sudo ./minibox run alpine /bin/sh
/ # cat /etc/alpine-release   # 호스트는 Ubuntu인데 alpine이 보인다
/ # rm /bin/ls && ls          # ls: not found
/ # exit
$ ls -l images/alpine/bin/ls  # 원본은 멀쩡하다
```

### 겪은 문제

- **`/dev/null`이 없어서 fork bomb 실험이 실패:** 쉘은 `&`로 띄운 백그라운드 작업의 입력을 `/dev/null`로 돌린다. `/dev`가 비어 있으니 폭탄 프로세스들이 cgroup 제한에 닿기도 전에 죽었다. → 원리 5의 최소 `/dev`를 만들었다.
- **`pivot_root` EINVAL:** 새 루트가 마운트 지점이 아니거나, 마운트 전파가 shared면 실패한다. minibox는 overlayfs로 마운트한 `merged`를 새 루트로 쓰고 `/`를 private으로 바꾼 덕분에 이 문제를 피했다.

## 3. 자원 제한: cgroup v2

### 배경지식

네임스페이스는 **보이는 것**만 나눈다. 컨테이너 하나가 메모리를 다 먹거나 프로세스를 무한히 만들면(fork bomb) 호스트 전체가 죽는다. 사용량을 제한하려면 cgroup(control group)이 필요하다.

### 원리

cgroup v2는 `/sys/fs/cgroup` 아래의 **디렉터리 트리**다. 디렉터리 하나가 그룹 하나이고, 그 안의 파일에 숫자를 쓰면 제한이 걸린다. 특별한 API 없이 파일 읽기와 쓰기만으로 조작한다.

```
/sys/fs/cgroup/
├── cgroup.subtree_control      "cpu memory pids"  ← 자식에게 쓸 수 있게 켠 컨트롤러
└── minibox/
    ├── cgroup.subtree_control  "+cpu +memory +pids"를 써서 켬
    └── minibox-2917922577/     ← 컨테이너 하나
        ├── cgroup.procs        이 그룹에 속한 PID들
        ├── memory.max          67108864   (64MiB)
        ├── memory.swap.max     0
        ├── cpu.max             50000 100000
        ├── pids.max            20
        ├── memory.events       oom_kill 1  ← 결과를 읽는 파일
        └── cpu.stat            usage_usec 7787856
```

| 파일 | 뜻 |
|---|---|
| `memory.max` | 메모리 상한(바이트). 넘으면 커널의 OOM killer가 그룹 안의 프로세스를 죽인다 |
| `memory.swap.max` | swap 상한. 0이 아니면 메모리를 넘겨도 swap으로 밀려나며 느려지기만 할 뿐 OOM이 나지 않는다 |
| `cpu.max` | `할당량 주기`(마이크로초). `50000 100000`은 "100ms마다 50ms만 CPU를 써라", 즉 0.5코어다 |
| `pids.max` | 프로세스 **및 스레드** 수 상한. 넘으면 `fork`가 실패한다(EAGAIN) |
| `memory.events` | `oom_kill` 등 사건 횟수 |
| `cpu.stat` | `usage_usec`: 지금까지 쓴 CPU 시간(누적) |
| `cgroup.kill` | 1을 쓰면 그룹 안의 모든 프로세스를 SIGKILL로 죽인다 |

**"no internal processes" 규칙:** 프로세스가 들어 있는 cgroup은 자식 cgroup에 컨트롤러를 나눠 줄 수 없다. 그래서 `minibox/` 디렉터리 자체는 비워 두고, 컨테이너마다 그 아래에 하위 디렉터리를 만든다.

### minibox에서는

`internal/cgroup/cgroup.go`

**태어날 때부터 cgroup 안에 넣기(`CLONE_INTO_CGROUP`):** 흔한 방법은 프로세스를 띄운 뒤 `cgroup.procs`에 PID를 쓰는 것이다. 하지만 그러면 띄운 순간부터 PID를 쓰기 전까지 아주 짧은 **제한 없는 틈**이 생긴다. fork bomb은 그 틈에도 불어날 수 있다. 리눅스 5.7부터는 `clone3`에 cgroup 디렉터리를 넘겨서 **처음부터 그 안에서 태어나게** 할 수 있다. Go에서는 `SysProcAttr.UseCgroupFD`로 쓴다.

### 직접 확인 (3주차 실험)

```bash
sudo ./minibox run --pids 20 alpine /bin/sh -c 'f(){ f|f & }; f; sleep 3'   # fork bomb
sudo ./minibox run --mem 64m alpine tail /dev/zero                          # 메모리 폭주
sudo ./minibox run --cpu 0.5 alpine sh -c 'timeout 5 sh -c "while :; do :; done"; true'
```

종료할 때 `[minibox] ...` 줄에 위 파일들에서 읽은 결과가 나온다. 실측 결과는 [EXPERIMENTS.md](../EXPERIMENTS.md)에 있다: 프로세스 20개에서 정지, 64.0MiB에서 OOM kill, 평균 0.50코어.

### 겪은 문제

- **`tail` 하나인데 `pids.peak`가 5:** pids 제한은 프로세스가 아니라 **태스크(스레드 포함)** 를 센다. `tail`로 exec하기 전의 minibox(Go 런타임)가 스레드를 여러 개 만들었던 게 잡혔다.
- **swap이 켜져 있으면 OOM이 안 난다:** Orin Nano에는 8GB swap이 있다. `memory.swap.max=0`을 함께 걸어야 실험이 의도대로 된다.

## 4. 네트워크: veth, 브리지, NAT

### 배경지식

- **IP 주소와 서브넷:** `10.88.0.2/24`에서 `/24`는 앞 24비트(10.88.0)가 같은 주소들이 **같은 동네(서브넷)** 라는 뜻이다. 같은 동네끼리는 직접 통신하고, 다른 동네로 갈 때는 **게이트웨이**(동네 출구)로 보낸다.
- **L2와 L3:** 같은 동네 안에서는 MAC 주소로 프레임을 주고받는다(L2, 스위치의 영역). 동네를 넘어갈 때는 IP로 라우팅한다(L3, 라우터의 영역).
- **사설 IP와 NAT:** `10.x.x.x`는 인터넷에서 쓸 수 없는 사설 주소다. 밖으로 나갈 때는 공유기가 출발지 주소를 자기 주소로 바꿔 준다. 이게 NAT다.

### 원리

새 net 네임스페이스에는 `lo`(자기 자신)밖에 없다. 여기에 밖으로 이어지는 길을 뚫어야 한다.

- **veth 쌍:** 양 끝이 이어진 **가상 랜선**이다. 한쪽에 넣은 패킷이 반대쪽으로 나온다. 한쪽 끝을 컨테이너의 net 네임스페이스로 옮기면, 컨테이너와 호스트가 연결된다.
- **브리지(`mb0`):** 소프트웨어로 만든 **스위치**다. 컨테이너마다 veth의 호스트 쪽 끝을 브리지에 꽂으면, 컨테이너들이 같은 동네가 된다. 브리지에 `10.88.0.1`을 주면 호스트가 이 동네의 게이트웨이 역할을 한다.
- **IP 포워딩(`ip_forward=1`):** 호스트가 한 인터페이스로 받은 패킷을 다른 인터페이스로 넘겨 주는(라우터가 되는) 기능이다.
- **MASQUERADE:** 컨테이너(`10.88.0.2`)가 인터넷으로 나갈 때 출발지 주소를 호스트의 와이파이 주소로 바꾼다. 돌아오는 응답은 커널의 연결 추적(conntrack)이 기억해 뒀다가 원래 컨테이너로 되돌린다.

```
 컨테이너 B (net ns)           호스트 (기본 net ns)                  컨테이너 A (net ns)
┌──────────────────┐   ┌─────────────────────────────────┐   ┌──────────────────┐
│ eth0 10.88.0.3 ──┼───┼─ mbv3 ─┐                 ┌─ mbv2 ┼───┼── eth0 10.88.0.2 │
└──────────────────┘   │        └── mb0 (브리지) ──┘       │   └──────────────────┘
      veth 쌍          │           10.88.0.1               │          veth 쌍
                       │              │ 라우팅 + FORWARD 체인
                       │              ▼
                       │   POSTROUTING: MASQUERADE (출발지를 172.20.0.95로)
                       │              │
                       │         wlP1p1s0 (와이파이) ──────┼──→ 인터넷
                       └─────────────────────────────────┘
```

- **A↔B:** 같은 브리지 안이라 라우팅 없이 스위칭만 한다. 그래서 ping의 ttl이 64 그대로다.
- **B→인터넷:** 게이트웨이(mb0) → 라우팅 → MASQUERADE → 와이파이.

### iptables가 패킷을 보는 곳

iptables는 패킷이 지나가는 길목(체인)마다 규칙을 건다. 이 프로젝트에 필요한 길목은 두 개다.

```
들어온 패킷 → [PREROUTING] → 라우팅 결정 ─┬→ [INPUT] → 호스트 자신의 프로그램
                                          └→ [FORWARD] → [POSTROUTING] → 나가는 장치
                                              ↑ 통과·차단        ↑ NAT(MASQUERADE)
```

### minibox에서는

`internal/network/network.go`

1. 부모가 `mb0` 브리지를 만든다(처음 한 번). iptables 규칙은 전용 체인 `MINIBOX`에만 넣는다.
2. `/run/minibox/ips/`에 파일을 `O_EXCL`로 만들어 빈 IP를 잡는다. 동시에 두 개가 떠도 같은 IP를 받지 않는다(간단한 IPAM).
3. 컨테이너를 띄운 뒤 veth 쌍을 만들고, 한쪽을 컨테이너 PID의 net 네임스페이스로 옮긴다.
4. `nsenter -t <PID> -n ip ...`로 **호스트의 ip 명령을 컨테이너 네트워크 안에서만** 실행해 eth0, IP, 기본 라우트를 설정한다.
5. 그동안 컨테이너는 **파이프에서 기다린다.** 부모가 설정을 마치고 파이프를 닫으면 그때 사용자 명령을 실행한다. 이렇게 하지 않으면 네트워크가 준비되기 전에 명령이 먼저 돌아 버린다.

### 직접 확인

```bash
sudo ./minibox run alpine /bin/sh     # 터미널 두 개에서 각각
/ # ip addr show eth0
/ # ping -c 3 10.88.0.1               # 게이트웨이
/ # ping -c 3 8.8.8.8                 # NAT 너머 인터넷
/ # ping -c 3 10.88.0.2               # 다른 컨테이너
```

### 겪은 문제

- **Docker가 설치된 호스트에서는 통신이 조용히 막힌다:** Docker는 FORWARD 체인의 기본 정책을 DROP으로 바꾸고, `br_netfilter`를 켜서 **브리지 안의 통신까지** iptables를 지나가게 만든다. → `MINIBOX` 체인을 FORWARD 맨 앞에 끼우고 `mb0` 트래픽을 허용했다.
- **DNS가 안 된다:** 호스트의 `/etc/resolv.conf`는 `127.0.0.53`(systemd-resolved)인데, 이 주소는 호스트 자기 자신이라 컨테이너에서는 닿지 않는다. → 컨테이너에 `nameserver 8.8.8.8`을 쓴다.

## 5. TCP 기초: seq, ack, 핸드셰이크

### 배경지식: 계층

```
┌──────────────┐
│ HTTP         │  응용: "GET / 주세요"
├──────────────┤
│ TCP          │  전송: 순서대로, 빠짐없이 전달 (포트 번호로 프로그램 구분)
├──────────────┤
│ IP           │  네트워크: 어느 주소로 보낼까 (최선을 다하지만 보장은 없음)
├──────────────┤
│ Ethernet     │  링크: 옆 장치까지 한 칸 이동 (MAC 주소)
└──────────────┘
```

IP는 패킷이 사라지거나, 순서가 바뀌거나, 중복돼도 신경 쓰지 않는다. 그 위의 **TCP가 이것을 믿을 수 있는 바이트 스트림으로 바꿔 준다.** 이 프로젝트의 후반부는 TCP가 이 일을 어떻게 해내는지를 보는 것이다.

### 원리 1: seq와 ack는 "바이트 번호"다

TCP는 보내는 데이터의 **모든 바이트에 번호**를 매긴다.

- **seq(sequence number):** "이 패킷의 첫 바이트는 몇 번이다"
- **ack(acknowledgment number):** "나는 여기 **직전까지** 다 받았다. 다음에는 이 번호를 줘"

첫 번호(ISN)는 보안을 위해 무작위로 정한다. 그래서 실제 숫자는 `3827714599`처럼 크다. Wireshark와 패킷 여행기는 읽기 쉽게 첫 번호를 0으로 빼서 보여 준다. 이것이 **상대 seq**다.

### 원리 2: 3-way 핸드셰이크

연결을 맺을 때 양쪽이 각자의 첫 번호를 알려 주고 확인받는다. 6주차에 실제로 캡처한 결과(B가 A에게 `wget`)는 이렇다.

```
  클라이언트 B                                 서버 A
     │ ── SYN            seq=0 ─────────────────→ │   "연결하자. 내 번호는 0부터"
     │ ←───────── SYN-ACK seq=0, ack=1 ────────── │   "좋아. 내 번호도 0부터. 네 1번을 기다릴게"
     │ ── ACK            seq=1, ack=1 ──────────→ │   "확인"
     │ ── 데이터 85B      seq=1, ack=1 ──────────→ │   HTTP 요청 (1~85번 바이트)
     │ ←───────── ACK     seq=1, ack=86 ───────── │   "85번까지 받았어, 86번을 줘"
     │ ←───────── 데이터 44B seq=1, ack=86 ─────── │   HTTP 응답
     │ ── ACK            seq=86, ack=45 ────────→ │
     │ ←───────── FIN     seq=45, ack=86 ──────── │   "나는 다 보냈어"
     │ ── FIN            seq=86, ack=46 ────────→ │   "나도. 그리고 네 FIN 받았어"
     │ ←───────── ACK     seq=46, ack=87 ──────── │
```

두 가지를 눈여겨보자.

1. **SYN과 FIN은 데이터가 없어도 번호를 1 차지한다.** SYN이 0번을 썼기 때문에 첫 데이터는 1번부터다. 응답 44바이트(1~44번) 뒤의 FIN이 45번이고, 그 FIN을 받았다는 ack가 46이다.
2. **종료가 4개가 아니라 3개다.** 교과서에는 FIN → ACK → FIN → ACK의 "4-way"로 나온다. 하지만 B는 A의 FIN에 대한 ACK를 **자기 FIN에 실어서** 한 패킷으로 보냈다.

### 원리 3: 윈도우

한 패킷을 보내고 ACK를 기다린 뒤 다음을 보내면 너무 느리다. TCP는 ACK를 기다리지 않고 여러 패킷을 연달아 보낸다. 얼마나 많이 보낼지는 두 가지가 정한다.

- **수신 윈도우(rwnd):** 받는 쪽이 "내 버퍼에 이만큼 남았다"고 패킷마다 알려 주는 값. TCP 헤더의 `win` 필드다.
- **혼잡 윈도우(cwnd):** 보내는 쪽이 "네트워크가 이만큼은 감당할 것 같다"고 스스로 추정한 값. 패킷에는 실리지 않는다. 6장에서 다룬다.

**보냈지만 아직 ACK를 못 받은 바이트(bytes in flight)** 는 이 둘 중 작은 값을 넘을 수 없다. 패킷 여행기의 "전송 중인 바이트" 그래프가 이것이다. cwnd는 캡처에 보이지 않으므로, 이 값이 cwnd를 가늠하는 단서(하한)가 된다.

## 6. TCP가 손실을 견디는 방법

### 원리 1: 손실을 알아차리는 두 가지 방법

**① 타임아웃(RTO):** 보낸 뒤 일정 시간(RTO) 안에 ACK가 안 오면 잃어버린 것으로 보고 다시 보낸다. RTO는 왕복 시간(RTT)을 재서 정하지만, 리눅스에서는 **최소 200ms**다. 다시 실패하면 대기 시간을 두 배씩 늘린다(지수 백오프). 확실하지만 느리다.

**② 중복 ACK와 빠른 재전송:** 받는 쪽은 중간이 비면 **같은 ack를 반복해서** 보낸다. 예를 들어 1~100, 201~300, 301~400을 받고 101~200이 비었다면, 새 패킷이 올 때마다 "101번을 줘"라고 계속 말한다. 보내는 쪽이 같은 ack를 **3번 더(중복 ACK 3개)** 받으면, 타임아웃을 기다리지 않고 바로 다시 보낸다. 이것이 빠른 재전송(fast retransmit)이다.

```
보내는 쪽                        받는 쪽
 1~100   ────────────────────→   ack 101
101~200  ─────── ✕ (사라짐)
201~300  ────────────────────→   ack 101  (중복 #1)
301~400  ────────────────────→   ack 101  (중복 #2)
401~500  ────────────────────→   ack 101  (중복 #3)
          ← 3번 받았다: 101~200이 사라졌구나
101~200  ────────────────────→   ack 501  (한 번에 쭉 전진)
```

### 원리 2: SACK, "어디가 비었는지" 정확히 알려 주기

ack만으로는 "101번이 비었다"까지만 알 수 있다. 그 뒤에 무엇을 받았는지는 모른다. **SACK(선택적 확인)** 은 TCP 옵션에 "대신 201~500은 받았어"라는 **받은 구간 목록**을 싣는다. 그러면 보내는 쪽은 정확히 빈 곳만 다시 보낸다.

최신 리눅스는 SACK와 **RACK**(시간 기반 손실 감지) 알고리즘을 함께 쓴다. 그래서 중복 ACK를 3번 기다리지 않고, **SACK 한 번만 보고도** 재전송할 수 있다. 10% 손실 캡처에서 실제로 이렇게 했다.

```
#10  A→B  데이터 8192B seq 8193            ✕ 사라짐
#11  A→B  데이터 7240B seq 16385
#12  B→A  ack 8193, SACK 16385~23625       "8193부터 비었고, 16385~23625는 받았어"
#13  A→B  데이터 7240B seq 8193            ⟲ 빠른 재전송 (#12로부터 0.02ms 뒤)
```

### 원리 3: 혼잡 제어, 손실은 "네트워크가 막혔다"는 신호

TCP는 패킷이 사라지면 **네트워크가 혼잡하다**고 해석하고 보내는 속도(cwnd)를 줄인다.

- **슬로 스타트:** 처음에는 작게 시작해서 ACK를 받을 때마다 cwnd를 키운다(RTT마다 대략 두 배).
- **혼잡 회피:** 어느 정도 커지면 천천히 늘린다.
- **손실 시:** 빠른 재전송이면 cwnd를 줄이고(리눅스 기본 CUBIC은 약 30% 감소) 이어 간다. 타임아웃이면 cwnd를 1로 되돌리고 처음부터 다시 시작한다.

그래서 **타임아웃이 훨씬 비싸다.** 기다리는 시간도 길고, 속도도 바닥부터 다시 올려야 한다.

### 원리 4: Mathis 공식, 손실률과 처리량

손실이 드물 때, 혼잡 회피 상태의 TCP 처리량은 대략 이렇게 추정한다(Mathis 외, 1997).

```
처리량 ≈ (MSS / RTT) × (1.22 / √p)       p = 손실률, MSS = 패킷당 최대 데이터(보통 1448B)
```

손실률이 4배가 되면 처리량은 √4 = 2배 떨어진다는 뜻이다. 그런데 minibox 실측에서는 1%에서 5%로 갈 때(√5 ≈ 2.2배 예상) **35배**가 떨어졌다.

| 손실률 | 처리량 | 재전송 |
|---|---|---|
| 0% | 21.3 Gbps | 0 |
| 1% | 2.07 Gbps | 17,739 |
| 5% | 59.1 Mbps | 2,815 |
| 10% | 7.86 Mbps | 606 |

공식은 **빠른 재전송으로 복구되는 상황**을 가정한다. 손실이 잦아지면 빠른 재전송마저 실패해서 타임아웃이 늘어나고, 그러면 공식이 맞지 않는다. 컨테이너 사이의 RTT는 0.05ms 수준인데 최소 RTO는 200ms로, **4,000배**나 길다. 타임아웃이 한 번만 나도 처리량이 무너진다. 10% 손실 중 300KB를 보낸 캡처에서는 타임아웃 두 번이 전체 416ms 중 412ms를 차지했다.

### 겪은 문제: 교과서 정의가 실제 리눅스와 달랐다

- **중복 ACK를 놓침:** 교과서(RFC 5681) 정의는 "ack와 **윈도우 값이** 같을 것"이다. 그런데 리눅스는 수신 버퍼를 자동으로 조절해서 ACK마다 윈도우가 조금씩 바뀌었다. → SACK 블록이 있으면 윈도우가 달라도 중복 ACK로 본다.
- **빠른 재전송을 타임아웃으로 오분류:** "중복 ACK 3번 = 빠른 재전송" 규칙은 SACK와 RACK가 있는 리눅스에 맞지 않았다. → 재전송 직전의 상황으로 분류한다.
  - 150ms 넘게 조용했다가 보냈다 → 타임아웃
  - 타임아웃 직후 ACK가 전진하기 전에 이어서 보냈다 → 타임아웃 후 복구
  - 중복 ACK나 SACK를 받은 직후에 보냈다 → 빠른 재전송

## 7. pcap 파일 직접 읽기

### 배경지식: 이진 파일과 엔디언

pcap은 텍스트가 아니라 **바이트를 정해진 자리에 늘어놓은** 이진 파일이다. 여러 바이트로 된 숫자를 저장하는 순서는 두 가지다.

- **빅엔디언:** 큰 자리부터. `0x0800` → `08 00`
- **리틀엔디언:** 작은 자리부터. `0x0800` → `00 08`

**네트워크 헤더(IP, TCP)는 항상 빅엔디언**이다("네트워크 바이트 순서"). 반면 **pcap 파일 헤더는 캡처한 컴퓨터의 순서**를 따른다. 그래서 파일 맨 앞의 매직 넘버로 판별한다. `a1 b2 c3 d4`로 읽히면 순서가 같은 것이고, `d4 c3 b2 a1`이면 뒤집힌 것이다.

### 구조

```
pcap 파일
├─ 글로벌 헤더 24B   매직 넘버, 버전, snaplen, linktype(1 = Ethernet)
├─ 패킷 레코드
│   ├─ 레코드 헤더 16B   초, 마이크로초, 저장된 길이, 원래 길이
│   └─ 패킷 바이트 ─────────────────────────────────────┐
├─ 패킷 레코드 ...                                       │
                                                        ▼
┌─ Ethernet 14B ──┬─ IPv4 (보통 20B) ─────────┬─ TCP (20B + 옵션) ─────────┬─ 데이터
│ 목적지 MAC  6B   │ 0   버전·헤더길이(IHL×4)  │ 0   출발지 포트 2B          │
│ 출발지 MAC  6B   │ 2   전체 길이 2B          │ 2   목적지 포트 2B          │
│ 타입 2B          │ 9   프로토콜 (6 = TCP)    │ 4   seq 4B                 │
│ (0x0800 = IPv4) │ 12  출발지 IP 4B          │ 8   ack 4B                 │
│                 │ 16  목적지 IP 4B          │ 12  헤더 길이(상위 4비트×4) │
│                 │                          │ 13  플래그 (FIN 1, SYN 2,   │
│                 │                          │     RST 4, PSH 8, ACK 16)  │
│                 │                          │ 14  윈도우 2B               │
│                 │                          │ 20~ 옵션 (SACK = 종류 5)    │
└─────────────────┴──────────────────────────┴───────────────────────────┘
```

데이터 길이는 `IP 전체 길이 − IP 헤더 길이 − TCP 헤더 길이`로 구한다. 캡처할 때 뒷부분이 잘려도(snaplen) 이 값으로 원래 길이를 알 수 있다.

### minibox에서는

`web/pcap.js`는 라이브러리 없이 JavaScript의 `DataView`로 위 표의 자리에서 바이트를 직접 읽는다. 읽은 패킷은 4-tuple(출발지 IP·포트, 목적지 IP·포트)로 묶어서 연결 하나로 만든다. 방향이 반대여도 같은 연결이다. 테스트는 `node --test web/`로 돌린다. 가짜 pcap을 바이트 단위로 만들어서 파서가 정확히 읽는지 확인한다.

### 겪은 문제

- **타임스탬프 정밀도:** `1700000000초 + 0.000044초`를 실수(double) 하나로 합치면, 큰 수 때문에 마이크로초 자리가 뭉개진다. → 첫 패킷의 초를 먼저 빼고 나서 소수부를 더한다.
- **MSS보다 큰 패킷(8192B):** 원래 패킷 하나에 담을 수 있는 데이터는 1448B 정도다. 그런데 veth에서는 커널이 큰 덩어리를 쪼개지 않고 한 번에 넘기는 최적화(GSO/TSO)를 해서, 캡처에 쪼개지기 전의 덩어리가 보인다.

## 8. 장애 주입

### 원리

TCP가 손실을 어떻게 견디는지 보려면 **일부러 패킷을 버려야** 한다. 보통은 `tc netem`을 쓰는데, Orin Nano의 커널에는 이 모듈이 빠져 있다. 그래서 두 가지로 대신했다.

- **손실: iptables `statistic` 모듈.** 규칙에 확률을 걸어 그 확률로만 DROP한다.
  ```
  iptables -A MINIBOX-CHAOS -i mb0 -m statistic --mode random --probability 0.1 -j DROP
  ```
- **대역폭 제한: `tc tbf`(토큰 버킷).** 양동이에 일정한 속도(rate)로 토큰이 쌓이고, 패킷은 토큰을 써야 나갈 수 있다. 양동이 크기(burst)만큼은 몰아서 보낼 수 있고, 그 이상 쌓인 패킷은 기다리다가(latency) 버려진다.

### 캡처 위치와 버리는 위치

`tcpdump -i mb0`는 패킷이 **브리지에 들어오는 순간**을 캡처한다. 버리는 규칙은 그 뒤 **FORWARD 단계**에서 동작한다. 그래서 **버려진 패킷도 캡처에는 남는다.** 덕분에 패킷 여행기는 재전송된 패킷의 **원본을 찾아서 "도중에 사라짐"으로 표시**할 수 있다.

```
컨테이너 A ─→ mbv2 ─→ mb0 ─[tcpdump가 여기서 복사]─→ FORWARD ─[여기서 10% DROP]─→ mbv3 ─→ 컨테이너 B
```

### minibox에서는

`internal/network/network.go`의 `Chaos`와 `ClearChaos`, CLI는 `minibox net chaos --loss 10% [--rate 1mbit]`와 `minibox net clear`다. 규칙은 전용 체인 `MINIBOX-CHAOS`에만 넣으므로, 해제는 체인을 비우기만 하면 된다.

## 9. 패킷 여행기 화면 읽는 법

[패킷 여행기](https://wnsrud2002.github.io/minibox/)를 열고 샘플 "패킷 10% 손실 중 300KB 전송"을 누른다.

| 화면 | 읽는 법 |
|---|---|
| 요약 칸 | 처리량은 재전송분을 뺀 실제 데이터(goodput)로 계산한다. 재전송은 종류별로 나눠 센다 |
| 전송 중인 바이트 그래프 | 5장 원리 3의 bytes in flight. 빨간 세로선이 재전송이다. 선이 오래 평평하게 이어지는 구간이 타임아웃으로 멈춘 시간이다 |
| 파란 화살표 / 주황 화살표 | 클라이언트 → 서버 / 서버 → 클라이언트 |
| ✕ 끊긴 화살표 | 나중에 같은 seq로 다시 보내진 원본. 도중에 사라진 것으로 추정한다 |
| ! 중복 ACK #n + SACK a~b | 받는 쪽이 "중간이 비었다, 대신 a~b는 받았다"고 알리는 중 |
| ⟲ 빠른 재전송 / 타임아웃 재전송 | 6장 원리 1의 두 가지 복구 방법 |
| 오른쪽 +시간 | 첫 패킷으로부터 흐른 시간. 0.3ms 다음이 206.9ms로 뛰는 곳이 RTO 대기다 |
| 문제 구간만 보기 | 재전송, 손실, 중복 ACK 앞뒤 3개씩만 남긴다 |

**따라가 볼 장면:** #10 사라짐 → #12 SACK로 빈 곳 알림 → #13 빠른 재전송(0.05ms 안에 복구) → 그런데 952B가 또 비어서 → 206ms 침묵 → #15 타임아웃 재전송.

직접 캡처한 파일은 파일 선택이나 끌어다 놓기로 열 수 있다. 파일은 서버로 올라가지 않고 브라우저 안에서만 파싱된다.
